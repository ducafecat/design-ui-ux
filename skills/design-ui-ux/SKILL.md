# Design UI UX

## 先判断任务

读取用户需求、项目约定和现有界面，选择适用路径。沿用已有选择与授权，不重复做已完成的决策。

| 任务 | 路径 |
| --- | --- |
| 新建设计或整体改版 | 明确范围 → 真实参考选型 → 风格访谈与确认 → 实现 → 验收 |
| 已提供具体可用参考、现有设计规范，或明确要求按指定风格直接制作 | 沿用依据，补齐影响实现的未知偏好；不重新模板选型 |
| 局部修改、增加沿用规范的页面 | 读取现有实现与相关设计规范，直接修改并验证受影响范围 |
| 视觉审查或答疑 | 给出有依据的发现与建议，仅在用户要求修改时改文件；不强制制作设计稿 |
| 明确跳过选型、访谈或确认 | 跳过指定阶段，说明实现假设，继续制作与验收 |

用户指定的技术、目录和交付格式优先。默认移动端仍是网页设计稿，不自动创建原生工程；不额外增加双主题、账号系统或其他未要求功能。

**产品名称不等于已完成选型。** “写个小红书 APP 移动端设计”等请求只明确了产品与目标端，默认仍走联网真实参考选型；不能仅凭熟悉该产品或能描述其风格就跳过。用户提供具体链接、截图、现有规范，或明确要求“照官方界面复刻”“按此风格直接做”“不用找参考”时，才沿用对应依据或跳过指定阶段。只给出配色、气质等偏好时，将其作为检索条件。

## 交付约定

- 默认最终成品为 **`design/index.html` 一个自包含文件**：业务视图、导航、交互、样式标准与面向用户的来源/验收记录均内置。使用原生 JavaScript 和文件内视图或 hash 路由，不拆出其他业务 HTML 或 `style-guide.html`。
- 实际使用 Tailwind 并把编译 CSS 内嵌；脚本、SVG、图片、字体、演示媒体和 JSON 同样内嵌。核心演示不依赖 CDN、相邻资源、相对 fetch 或运行时构建。具体实现约束见 [设计规范](references/design-standards.md)。
- `design/preview.html` 是独立的参考选型产物，同样自包含；截图原件、选择记录与构建源文件可以另存，但不作为最终成品的运行依赖。
- 样式标准提供文件内入口与返回路径，展示成品实际使用的颜色、字体、间距、断点及组件状态。演示数据与未接后端的操作明确标注，不冒充真实服务结果。
- 先检查既有 `design/` 内容归属；需要独立作品时用子目录并同步调整全部产物路径，不覆盖无关文件。

## 工具与依赖

- 浏览器遵从用户指定；否则有 `ego-browser` 技能时优先 Ego Lite，先读取其说明并按要求初始化。该技能或工具不可用时采用可用浏览器，不假定固定命令一定存在。检索、截图与验收使用同一选择规则。
- 所有浏览器均不可用时，明确哪些参考或运行检查未完成；可以继续不依赖浏览器的准备与实现，不伪造截图或通过记录。
- Python 3 仅用于本地数据检索。需要时读取 [检索指南](references/search-guide.md)，不预加载全部 CSV。检索建议不能覆盖用户已选风格，也不能代替浏览器验收。
- 制作前确认可用的 Tailwind 编译方式；若编译不可用，说明缺口并确定可行替代，不把手写 CSS 标成已编译 Tailwind。用户要求严格使用 Tailwind 时需解决该依赖后再声明完成。

## 完整设计流程

### 1. 明确范围

提取业务、受众、目标端、页面范围、技术和保存位置，给出简短摘要。

需要用户选择时先读取 [提问格式](references/question-format.md)。问题须包含具体选项和回复方式；回合结束仍待回答时，回复需自包含，不能只提示“请在上方选择”。目标端未知时只问“移动端还是 PC 端”；用户已要求两端则覆盖两端。业务用途缺失且影响参考检索时，单独澄清。次要细节自行判断，不把实现细节变成问卷。

### 2. 真实参考选型

默认新建设计在业务和目标端明确后立即进入本步骤，不先让用户从自行编造的风格方向中选择。读取 [真实参考选型](references/reference-selection.md)，实际使用联网检索与浏览工具考察至少 **5 个相关来源网站**，每轮用 **6 张不同样稿的真实截图** 制作自包含选型页。完成截图、放大与来源链接检查后再交付预览入口并询问选择。模型记忆、本地样式数据库和纯文字风格菜单均不能代替这一步。

页面选择标记只是本地状态，用户需在对话回复编号。选中后进入访谈；换批则保留可追溯编号和反馈。缺少截图时说明真实缺口，不用生成图或示意图顶替。

### 3. 访谈并确认风格

需要提问时读取 [提问格式](references/question-format.md)，按需读取 [风格访谈](references/style-interview.md)。一次只问一个问题，选项用具体视觉效果说明差异；给足适用方向，不凑数量，也不重复已知偏好。

围绕选定参考补齐整体气质、业务重点、主要记忆点及关键偏好。信息足够后停止，给出简短风格定义：概念、布局、配色、字体、图像/材质、动效、1–2 个辨识度细节与避免事项，区分用户选择和设计建议。

只问一次对该方案的确认，收到同意后实现；已有明确授权或用户明确免确认时直接推进。未回复、默认选中或浏览页面不视为同意。

### 4. 实现

制作预览页或最终界面前读取 [设计规范](references/design-standards.md)，按已确认范围实现。将全部业务视图及 `#style-guide` 等样式标准视图放入同一成品，保留可用导航、返回、刷新和深链接。

局部修改沿用现有结构与规范，只调整本次涉及的组件、状态和相应说明。检索仅在缺少具体设计依据时使用。

### 5. 验收与交付

读取 [验收清单](references/delivery-checklist.md)，按目标端及实际功能验证。默认单文件成品需复制到空目录，以 `file://` 打开检查自包含性；HTTP 预览只作补充。非默认技术按其实际运行方式验证。

记录实际视口、关键操作、观察结果与限制；修复后重查受影响项。交付成品链接、内置样式标准入口、打开方式、文件大小、截图与验证结果。没有执行的检查标为未验证。
